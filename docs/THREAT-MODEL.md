# Threat model

Scope: this package holds a durable contract and answers "may the loop continue?"
It executes no work, spawns no process, and opens no socket. Most of the risk is
therefore in what it *stores*, what it *asserts*, and what it *writes into the
user's config*.

| Threat | Impact if unmitigated | Mitigation | Residual risk |
| --- | --- | --- | --- |
| **Prompt injection** via workspace files, issue text, tool output | Injected text redefines the objective, so the loop "legitimately" continues on attacker-chosen work | The objective, scope, completion test and permitted sources are frozen at `start` and are never rewritten by any later command. `wake` restores the contract and cannot edit it (asserted). Queue items are data, never contract fields; anything outside the objective must carry `approvedByUser`, which `status` displays. | An injected string can still *reach* the model through the workspace. This package bounds what the loop may treat as its goal; it cannot sanitize the model's context. Keep `--scope` narrow. |
| **Malicious workspace files** (a repo that ships its own `.codex` config) | Config poisoning, wider authority | We only ever read/write under `$CODEX_HOME`, never inside the workspace. The workspace path is stored resolved and used only as a lock identity. | If Codex itself loads project-level instruction files, that is outside this package's control. |
| **Corrupted or truncated state** | Loop resumes on half-written nonsense | Atomic write (tmp + rename), so a crash leaves the last good file. Reads validate JSON shape, schema version, required fields, and a SHA-256 checksum over a canonical (key-sorted) serialization. Every failure mode has its own error code and makes `should-continue` return false. | None material; a fully deleted state dir simply means "no run". |
| **Tampered state** (hand-edited to widen scope or reset the cycle counter) | Silent authority escalation | Checksum mismatch → `TAMPERED_STATE`, refuses to run. | **The checksum is integrity, not authentication.** Anyone who can write the file can recompute it. It stops accidental corruption and casual edits, not a determined local attacker — who, having write access to `$CODEX_HOME`, could edit the hook itself anyway. Stated plainly rather than dressed up with an HMAC whose key would sit in the same directory. |
| **Duplicate runners** on one workspace | Two loops interleaving writes; lost work | `O_EXCL` create is the mutex — no check-then-create race. Second runner gets `LOCKED`. `should-continue` re-verifies that the lock token still matches the state's token, so a runner that lost ownership halts. | Two runners with *different* `CODEX_HOME`s pointed at one workspace are not detected by the state file; the lock lives under `CODEX_HOME`. Documented in LIMITATIONS. |
| **Stale lock** after a crash | Workspace permanently unusable | Reclaim only when the recorded pid is not alive *and* the heartbeat is older than 15 minutes; the reclaim records whom it displaced. | PID reuse could make a dead owner look alive, which fails *safe* (refuses to reclaim). |
| **Unreadable lock file** | Ambiguity resolved by stealing the workspace | Fails closed with `LOCK_UNREADABLE`; never assumes it is free. | Requires manual inspection — intended. |
| **Infinite loop / runaway spend** | Unbounded cycles, unbounded cost | Hard `maxCycles` cap (default 25, max 500) that sets `blocked` and cannot be cleared by `unblock` (`CAP_EXCEEDED`); queue capped at 200. | The cap is per run; a user who repeatedly force-starts new runs is choosing that. |
| **Retrying the same wall forever** | Looks busy, achieves nothing, burns tokens | Same blocker for 3 consecutive cycles with no new route → `blocked`, advancing stops, the smallest required user action is surfaced (and carried forward from the first sighting). | Blocker identity is string equality on the summary; a caller that varies the wording each cycle defeats the counter. Callers should pass a stable summary. |
| **Resurrection after stop/completion** | The user "stopped" it and a heartbeat restarts it | `completed` and `stopped` are terminal; `wake` refuses. `stop` writes a tombstone that outlives the state file, so recreating state does not resurrect the run. `start` after a stop requires explicit `--force`. | A user deleting the whole `persistent/` dir is starting fresh deliberately. |
| **Approval / sandbox bypass** | The whole point of the safety rules | No code path in this package executes Codex or any command. The installed hook runs `node persist.js should-continue`. A test asserts no bypass flag string appears in anything we install. | If the *user* wires our verdict into their own bypassing wrapper, that is their wrapper's behavior, not this package's. |
| **Secret leakage into state or logs** | Credentials persisted in plaintext, possibly synced | `assertNoSecrets` runs before every write to state and log, rejecting PEM private keys, `sk-`, `ghp_`/`gho_`/`ghu_`/`ghs_`/`ghr_`, `xox*`, `AKIA…`, 32-byte hex, and `key=/secret=/token=/password=` shapes. A rejected contract creates no state and takes no lock. Files are written `0600`. | Pattern matching is a guard, not a guarantee — a novel credential format can slip through. Never paste credentials into an objective, queue item, or blocker; pass a reference. |
| **Hidden telemetry / exfiltration** | Objectives leaving the machine | Zero dependencies (`"dependencies": {}`), zero network calls anywhere in `src/` or `bin/`. Auditable in a few hundred lines. | None. Verify with `grep -rn "http\|fetch\|net\|dns" src bin`. |
| **Destroying user configuration** | Losing a hand-tuned Codex setup | Plan-then-write; refuse on anything unparseable or conflicting; back up originals before any write; idempotent; uninstall restores baseline bytes or surgically removes only our additions. Twelve install/uninstall tests cover these paths. | A `config.toml` whose `[persistent_mode]` we *did* write and the user then edited is restored by block removal, not baseline bytes — their edits inside our block are lost. Edit outside the fence. |

## Non-goals

- This is not a sandbox, and it does not audit what the loop does inside the
  workspace. Codex's own sandbox and approval settings remain the enforcement
  boundary; nothing here relaxes them.
- It does not defend `$CODEX_HOME` against a local attacker who already has
  write access there.
